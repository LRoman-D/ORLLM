StepORLM 复现两阶段实施方案
面向本地 4060 8GB 与 AutoDL 云端的可执行路线
版本定位：可跑通闭环、可展示项目经验、可为后续 OR+LLM 研究扩展
一页结论
1. 一阶段不要追求论文同规模复刻；目标应改为“小模型 + 轻量数据工厂 + solver 验证 + 最小自进化闭环”。
2. 二阶段上云后再补齐 7B/8B policy、GenPRM、W-DPO、多轮 rollout 与基准测试。
3. 你手头的 OR 书籍优先用于教师端 RAG 与知识卡片库，不建议直接拿去微调教师模型。
4. 最终项目可同时包装成“后训练微调项目 + solver-in-the-loop agent 项目 + OR 领域化应用项目”。
1. 项目目标与总体取舍
本方案不按论文原始配置直接复刻。原文使用 Qwen3-8B、50K 合成问题、8×H100 80GB、8192 上下文和多轮 self-evolving 训练，这对本地 4060 8GB 不现实。正确策略是先构建“可运行、可验证、可展示”的缩减闭环，再在云端补齐规模化组件。

2. 一阶段方案：本地 4060 8GB 可执行路线
一阶段的目标不是追求论文数值，而是让整个链条在你的电脑上“完整跑通”。建议优先选择 Linux/WSL2 环境；Windows 原生可开发，但 Python、求解器和多进程执行隔离更容易踩坑。
2.1 一阶段目标定义
基于 3~5 类 OR 模板自动生成 1000~3000 条训练样本。
完成一个 1.5B policy 模型的 QLoRA/SFT 微调。
完成 solver 执行器与错误回流修正。
完成一次迷你自进化：每题采样 2~3 条轨迹，构造最简单的 preference 对。
在小规模测试集上给出 Pass@1、可执行率、可行率。

2.3 一阶段数据生成逻辑
建议用“程序模板打底 + 教师模型润色 + solver 验证”的三段式，而不是纯 LLM 自由生成。这样最稳，也最适合让 Codex 在本地快速实现。
2.3.1 先做 5 类模板
线性资源分配（LP）
生产计划 / 配方优化（LP/MILP）
分配 / 运输（assignment / transportation）
0-1 背包 / 资本预算（MILP）
小规模 TSP / 路径选择（5~8 节点）
每个模板都要有：参数采样器、可行性检查器、标准数学结构、标准 solver 代码、可转写成自然语言的槽位。
2.3.2 生成流程
程序先随机采样参数，保证实例可行且数值尺度合理。
程序生成结构化问题描述，再调用教师模型改写成自然语言题目。
教师模型按固定输出格式生成 <step> 分步建模、数学模型和 solver 代码。
本地执行代码；若报错或无最优解，则将错误信息回喂教师模型进行有限次修正。
保留通过验证的样本，写入 train/valid/test JSONL。
2.4 一阶段训练计划
2.4.1 Policy 模型
模型：Qwen2.5-1.5B-Instruct。
方式：QLoRA 4-bit，LoRA rank 16 或 32。
序列长度：2048 起步，必要时 3072；不要一开始追 8192。
数据量：先用 1000~1500 条高质量样本跑通；再增至 3000 左右。
训练目标：让模型稳定输出固定章节顺序与可执行代码，而不是先追求复杂推理华丽度。
2.4.2 Mini-GenPRM / 轻量评审器
本地阶段不建议一开始完整训练论文式 GenPRM。
先用教师模型对完整轨迹做 retrospective review，输出每一步 Correct / Incorrect + 原因。
若显存允许，再训练一个 0.5B~1.5B 的小评审器，仅用于“轨迹对比排序”或“步骤纠错提示”。
本地阶段的目标是有评审信号，不一定要完全复制论文中的共进化 critic。
2.4.3 一次迷你自进化即可
每题采样 2~3 条轨迹；不要一开始就 4~8 条。
先使用最简单偏好构造规则：solver 成功 > solver 失败；若都成功，则目标值更优者胜；若都失败，则教师评分更高者胜。
先做 1 次 preference 训练或 reranking 验证，不要在一阶段堆太多迭代。
2.5 一阶段评测与通过标准
代码可执行率 ≥ 60%。
solver 可行/最优率持续上升。
在自建测试集与 benchmark 子集上，Pass@1 相比 base instruct model 有明确提升。
至少形成一个完整 demo：输入自然语言 OR 问题，输出步骤、模型、代码、求解结果。

3.2 二阶段需要新增或升级的模块
把 policy 升级到 7B/8B，并保留一阶段模板数据工厂。
把教师模型的 retrospective review 数据积累起来，正式训练 GenPRM。

把 benchmark 扩展到 NL4Opt、MAMO、NLP4LP 子集；再逐步加入更难子集。
3.3 二阶段云端训练顺序
先复用一阶段训练好的小模型和数据工厂，重新生成更大规模数据。
先做 7B/8B policy 的 SFT，不要一开始同时训 policy 和 GenPRM。
再用当前 policy rollout 产生多条轨迹，调用 solver 和教师/评审器打标签。
基于这些轨迹做一轮 W-DPO 对齐。
最后单独训练或继续微调 GenPRM，并做 inference-time verifier 实验。
3.4 二阶段建议的 benchmark 路线
第一批：NL4Opt、MAMO EasyLP、NLP4LP。
第二批：MAMO ComplexLP、ComplexOR。
第三批：IndustryOR 或你自己构造的物流/船运场景集。
评测指标至少保留 Pass@1、代码可执行率、solver 成功率、目标值匹配率。
4. OR 书籍：放进教师模型 RAG，还是微调教师模型？
结论先行：优先做教师端 RAG，不建议直接拿这些 PDF 去微调教师模型。即使后续做微调，也应微调你自己整理出的“高质量知识卡片与示例数据”，而不是直接用整本书原文。
4.1 为什么优先选 RAG
这些书是稳定知识，但内容跨度大、章节冗长，直接微调会把大量低相关文字一起喂进模型，性价比低。
RAG 可以精确检索“建模范式、经典约束、对偶/凸优化/整数规划概念、概率过程背景”，对教师生成和教师评审都更有帮助。
RAG 更易更新：后续你可以继续加入论文、solver 文档、自己的错误案例。
若书籍存在版权限制，RAG 作为你个人本地检索工具风险通常更可控；直接训练并传播模型则更敏感。

4.3 最实际的书籍处理方式
不要把整本 PDF 直接全部向量化后就结束；先按章节、定义、例题、建模套路切分。
优先抽取“可复用知识卡片”：变量定义套路、目标函数模板、常见约束、整数线性化、TSP/assignment/knapsack 标准建模。
对书中例题，手工或半自动整理成“小问答 + 标准建模要点 + 代码雏形”的结构化记录。
把这些知识卡片喂给教师端 RAG；后续若要微调，再从这些结构化卡片出发。
5. 如何把这个项目包装成“后训练 + Agent + OR”经验
你的目标不应只写成“复现论文”，而应写成“我构建了一个 solver-grounded 的 OR 领域 LLM 训练与 agent 闭环”。这样更容易打动实习面试。
5.1 项目叙事建议
后训练视角：SFT、QLoRA、preference construction、DPO/W-DPO、judge/verifier。
Agent 视角：问题生成、检索增强、代码生成、solver 执行、错误回流、自动修正、结果选择。
领域视角：把自然语言 OR 问题映射为数学模型与求解代码。
工程视角：数据工厂、执行沙箱、日志系统、benchmark harness。
5.2 简历上可落的表述方向
搭建了 OR 领域数据合成与 solver 验证流水线，实现自然语言问题到建模代码的自动生成与校验。
基于 Qwen 系列模型完成本地 QLoRA/SFT 微调，并构建多轨迹采样、偏好构造与 reranking 闭环。
设计教师端 RAG 知识库，融合经典 OR 教材、solver 文档与错误案例，提升生成与评审稳定性。
在 AutoDL 上扩展至 7B/8B 模型与 benchmark 测试，形成可展示的后训练与 agent 项目经验。
